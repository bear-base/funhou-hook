# llm-integration

分報(summary)生成を担うプロバイダ層の設計と運用方針。

## このドキュメントの位置づけ

これは基本設計レベルの方針整理である。詳細設計・実装計画は別途進める。

本ドキュメントは設計の方針と判断軸を示すものであり、実装の網羅性を要求するもの
ではない。「漏れなく実装する」より「方針に沿って判断する」ことを優先する。

関連ドキュメント:

- `docs/summary-engine.md`: 分報の生成タイミングや配送の設計(利用側)
- `docs/debug/summary-engine-llm-integration.md`: LLM 統合で迷走した経緯と教訓

## 目的

- 分報生成を「分報を作る」という用途レベルで抽象化する
- 上位層(SummaryEngine)が生成方法の詳細を知らずに済む構造にする
- LLM API の変化(モデル廃止、仕様変更、挙動の差異)に強い構造にする

## 設計の中核方針

### 「分報を作る」を抽象化する

抽象化の単位は「LLM クライアント」ではなく「分報を作る」という用途。

- 上位層は「分報がほしい」とだけ依頼する
- プロバイダが生成方法(LLM 利用、プロンプト構築、レスポンス処理等)を担う
- プロンプト設計もプロバイダ内部の責務

### 現時点では Gemini にフォーカス

- 現行実装は Gemini を使う具象プロバイダ(`GeminiSummaryProvider`)
- 過剰な抽象化(複数プロバイダ同時運用等)は避ける
- ただし、別プロバイダへの交換が必要になれば、新しい具象クラスを実装するだけで済む構造にする

## この設計の利点

「分報を作る」という用途レベルで抽象化することで、以下の利点がある。

### テストが作りやすい

- `FakeSummaryProvider` を作って固定の分報を返すだけで、上位層のテストが書ける
- LLM API のモック、プロンプト構築のモック等、複数レイヤーをモックする必要がない
- 「LLM 側の問題」と「上位層の問題」を独立して切り分けられる

### 今後の拡張がしやすい

- 別の LLM プロバイダへの乗り換えは、別の具象クラスを実装するだけ
- LLM を使わない実装(ルールベース、固定文等)も同じインターフェースで成立する
- インターフェースが用途と一致しているため、生成方法の選択肢が広い

### アップデートで壊れても修正方針が一貫する

- モデル廃止、API 仕様変更、新しい挙動の追加などは必ず起こる
- これらの変更は **該当プロバイダの内部修正だけ** で吸収できる
- 上位層への波及がないため、「壊れた時に何を直すか」が一貫している
- 修正の影響範囲を予測しやすい

## インターフェース設計

### SummaryProvider(抽象)

責務: ログを受け取り、分報メッセージを返す。

期待されるシグネチャ(目安):

- 入力: ログ群(時系列の `LogMessage` など)、トリガー種別(`Stop` / `PermissionRequest`)
- 出力: `SummaryMessage`(成功時)/ `None`(分報不要・失敗時)

### 期待される振る舞い

- **成功時**: `SummaryMessage` を返す
- **分報不要**: 内容が要約に値しないと判断した場合は `None` を返す(エラーではない)
- **失敗時**: `None` を返し、内部でエラーをログに記録する。例外は外に出さない
- **タイムアウト**: 一定時間内に結果を返す(分報がブロッキング要因にならない)

### エラーは内部で吸収する

分報はベストエフォート機能であるため、プロバイダ層で発生したエラーは外に伝播させない。

- LLM API エラー(レート制限、サーバーエラー、出力切れ等)は内部で処理
- 失敗時は `None` を返し、ログに詳細を残す
- 上位層は「分報が来なかった」とだけ認識する

## 現行実装(GeminiSummaryProvider)の方針

Gemini API を利用する具象プロバイダの実装方針。

### モデル選定の方針

分報生成に使うモデルは以下の観点で評価して選ぶ。

#### 評価軸

- **出力品質**: 分報として必要な情報量と読みやすさ
- **安定性**: 出力切れ、parse 失敗等が起きにくいか
- **レイテンシ**: 分報生成がブロッキング要因にならないか
- **コスト**: 利用頻度に対して許容できるか
- **モデルライフサイクル**: 廃止スケジュールが近くないか

#### 留意点

- **thinking model の挙動**
  - thinking tokens が出力枠を圧迫する可能性がある
  - 使う場合は `max_output_tokens` と thinking budget の両方を制御する必要がある
  - 出力品質と引き換えのトレードオフがあるため、両方試して比較する
- **stable版指定の重要性**
  - `-latest` 系は実体が変わる可能性があるため、本番運用では避ける
  - 検証用に `-latest` を使う場合は、実際にマップされたモデル名をログから確認する
- **軽量モデルの位置づけ**
  - コスト・レイテンシで有利
  - ただし出力品質が分報用途に十分かは要検証

#### 現行選定の記録

選定したモデルとその理由を本ドキュメントに記録する:

- 選んだモデル
- 選定の理由
- 試した代替案と評価結果
- 廃止スケジュール把握状況

### 必須の API 設定

- **`max_output_tokens` を明示する**
  - 出力切れを防ぐため、想定出力サイズに対して十分な値を設定
- **structured output(`responseSchema`)を使う**
  - JSON 出力を強制し、parse 失敗を構造的に防ぐ
- **thinking budget の制御**(thinking model を使う場合のみ)
  - 0 にして thinking を無効化する、または budget を明示的に設定する

### 外部 API 利用におけるエラーハンドリングと可観測性

#### 外部 API 利用のリスク認識

LLM API は内部システムではなく外部サービスへの依存であるため、内部関数を呼ぶ
ような扱いは適さない。以下の観点を踏まえた設計が必要:

- **外部依存としての切り離し**
  - API 障害や応答遅延が、システム全体の動作を止めない構造にする
  - 分報生成はベストエフォート扱いとし、失敗時はスキップして次に進む

- **レスポンス内容の検証**
  - 「呼び出して結果を受け取れたら成功」ではない
  - 出力切れ、内容の不整合、想定外フィールドの欠落など、レスポンスが成功扱いでも
    内容が壊れているケースがある
  - レスポンス構造を踏まえた検証ロジックが必要

- **エラー時の情報収集設計**
  - 単にエラーをログに出せばいいのではなく、原因特定に必要な情報が後から取れる
    設計をする
  - ログに何を残すか、どう残すかを API 仕様に即して検討する

これらは API 仕様調査フェーズで具体的に洗い出し、詳細設計に反映する。

#### エラーハンドリングの方針

- API 仕様に基づいてエラー種別を分類する
- 種別ごとに適切な対処を定義する(リトライ、諦め、ログのみ等)
- 「parse 失敗ならスキップ」のような汎用処理は避ける
- 種別の分類と対処は、API 仕様調査フェーズで網羅的に洗い出す

#### 可観測性の方針

エラーハンドリングを支える情報源として、ログを設計する。

- API レスポンスの構造を踏まえて、必要な情報を漏れなくログに出す
- 「動かしてみて足りなかったら追加」ではなく、最初から API 仕様に即したログ設計
  を行う

ログ設計の基準:

- 何が起きたかが即わかる(エラー種別、終了理由など)
- トークン消費の全容がわかる(入力、出力、内部処理を含む)
- モデルの実体がわかる(別名やマッピング先を解決した結果)
- 再現に必要な情報が揃う(リクエストパラメータ、レスポンスメタデータ)

具体的なエラー種別とログ項目は、利用するプロバイダの API 仕様に応じて詳細設計時
に定める。今回判明した教訓は `docs/debug/summary-engine-llm-integration.md`
を参照。

## プロバイダ交換時の運用

### モデル変更時の手順

LLM API は変化が激しいため、モデル変更を運用イベントとして扱う。

- モデル変更時は動作確認を必須とする(自動吸収はしない)
- 変更前のモデル挙動を記録しておく(本ドキュメントの「現行実装の方針」を更新)
- 廃止スケジュールを定期的に確認する

### 別プロバイダへの交換

別 LLM プロバイダ(Claude、OpenAI 等)への交換が必要になった場合:

- 新しい具象クラス(例: `ClaudeSummaryProvider`)を実装する
- 既存の `GeminiSummaryProvider` は残す or 削除を判断する
- インターフェースは変えない(上位層への影響なし)

## やらないこと(意図的な非ゴール)

- **複数プロバイダの同時運用**(現時点では不要、過剰)
- **モデルの自動切り替え**(運用イベントとして人間が判断する)
- **エラーの自動回復**(失敗時は諦めて次のトリガーを待つ、ベストエフォート機能)
- **LLM 抽象化レイヤー**(プロバイダの中の話、外には出さない)
- **過剰な堅牢性追求**
  - 分報はベストエフォート機能であり、完璧な可用性は求めない
  - リトライ戦略やエラー処理は、用途に対して過剰にならない範囲で設計する
  - 具体的な範囲は実装提案時に判断軸として議論する
- **過剰な可観測性追求**
  - デバッグに必要な情報を出すことが目的であり、メトリクス収集や監視基盤化が
    目的ではない
  - 「あれば便利」ではなく「必要だから出す」を判断軸にする

これらは、必要性が顕在化した時点で再設計する。

## 進め方

1. **基本設計(本ドキュメント)**
   - 設計の中核方針、利点、インターフェース、運用方針を整理

2. **API 仕様調査**
   - 利用予定の LLM プロバイダの公式ドキュメントを最新で確認する
   - 入出力トークン制限、レート制限、料金、廃止スケジュール
   - レスポンス構造(エラー種別、メタデータ、内部処理に関する情報)
   - structured output、thinking budget 等の制御パラメータ
   - デバッグに必要なログ項目を網羅的に洗い出す
   - エージェントの学習データに頼らず、必ず公式情報で確認する

3. **詳細設計**
   - API 仕様調査の結果を踏まえてインターフェースを具体化
   - 現行プロバイダ実装の方針を確定(モデル選定、必須設定、エラー処理)
   - ログ設計(API レスポンス構造に即したものを最初から用意)

4. **実装計画**
   - 既存コードからの移行、テスト整備、段階的な変更計画

5. **実装**

基本設計が固まる前に詳細設計に進まない。
API 仕様調査が終わる前に詳細設計に進まない。
