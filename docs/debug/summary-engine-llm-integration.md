# Summary Engine LLM 統合 Debug Notes

## 目的

funhou-hook の summary engine で LLM(Gemini API)を使うときに、
モデル選定や API 利用の理解不足で迷走したポイントを残す。
詳細な設計方針は `docs/llm-integration.md` を参照する。

## 起きたこと

- summary が parse 失敗で破棄され続けていた
- 表面的なエラー(invalid JSON)だけ見ていた
- 詳細ログを段階的に追加してようやく原因が判明
- 真因: thinking model で `MAX_TOKENS` 切れ、出力 10 トークンしか出ていなかった
- 対症: モデルを flash-lite 系に変更したところ正常に動作した

## つまずいた点

### 0. エージェントが古いバージョン/古いモデルを前提に設計していた

- エージェントは学習時点の情報で提案するため、最新の API・モデル状況を把握していない
- 今回は `gemini-2.0-flash` 前提で設計が組まれていたが、実際には2026年3月に
  廃止予定のモデルだった
- これは AI 系 API に限った話ではなく、ライブラリのバージョンでも同様に起きる
  - 古いバージョン前提のコードが提案されてエラー、レスポンスがおかしい等
- AI 系 API では特に頻繁に起きる
  - 通常の API(REST、DB等)と違い、数ヶ月スパンで大きな変更がある
  - 後方互換は保たれず、stable版でも廃止される
- ユーザー側が意識すべきこと:
  - エージェントの設計提案を鵜呑みにせず、モデル/ライブラリ選定は最新情報で確認する
  - 「動いたから良い」ではなく「使い続けられるか」を判断軸に入れる
  - AI 系 API は通常の API より一段慎重に設計する

### 1. lite と thinking 系で MAX_TOKENS の挙動が違う

- 同じ「flash 系」でも、thinking model は thinking tokens を消費する
- thinking budget(今回 487 トークン)が出力枠を圧迫し、本文用の出力が
  10 トークンしか残らなかった
- ユーザー側に「モデル系統で挙動が違う」認識がなかった
- `gemini-flash-latest` を指定していたが、実体は `gemini-3-flash-preview`
  にマップされていた
- → モデル選定では系統(thinking 有無、stable版か否か)を確認する必要がある

### 2. レスポンスの見るべき箇所が違っていた

- 最初は parse 失敗のテキスト内容だけ見ていた
- 真因の特定には以下のフィールドが必要だった:
  - `finishReason`: 出力切れか正常終了か
  - `usageMetadata.candidatesTokenCount`: 実際の出力トークン数
  - `usageMetadata.thoughtsTokenCount`: thinking tokens 消費量
- レスポンスの構造を理解せず、テキストの spot check だけしていた

### 3. ログ設計が API 利用に即していなかった

- 「動かしてみて足りなかったら追加」という後追いだった
- API レスポンスの構造を踏まえた最低限のログが最初から出ていれば、迷走しなかった
- 出すべきログ:
  - `finishReason`
  - 入力/出力/thinking のトークン数
  - 実際に呼び出されたモデル名(`-latest` 解決後の実体)

### 4. エラーハンドリングが汎用的すぎた

- 「parse 失敗ならスキップ」という雑な処理だった
- LLM API 特有のエラー種別(MAX_TOKENS、レート制限、サーバーエラー、
  内容違反等)を区別できていない
- 結果として、エラーが起きても「何が起きたか」がログからも分からない

## 教訓

- **エージェントの設計提案は学習時点の情報に基づく。依存(モデル、ライブラリ等)
  の選定は最新情報を確認した上で決める。特に AI 系 API は変化が激しい**
- LLM API は「呼べば返ってくる」と扱わず、レスポンス構造を理解して使う
- モデル選定は系統(thinking 有無、stable版か否か)を確認する
- ログは API レスポンスの構造に即して最初から設計する
- エラーは種別を区別して扱う
- 詳細な設計方針は `docs/llm-integration.md` を参照
